Dyslexia Grand Hub - Monorepo Structure

Version: 1.0 Date: 2026-10-31 Author: Senior Tech Lead (Devin) Status: Architecture Phase - Complete

Package Management Strategy

Choice: npm workspaces Justification:
  • Native npm support (no additional tooling)
  • Simple configuration
  • Good TypeScript support
  • Compatible with all major CI/CD platforms
  • Sufficient for our needs (not as complex as nx/pnpm workspaces needed)

Shared Packages and Their Purposes

packages/core

Purpose: Platform-agnostic business logic Contains:
  • Domain models and interfaces
  • Domain services (screening, intervention, user profile, research, sync)
  • Repository interfaces (agnostic implementations)
  • Shared utilities (date, validation, i18n)
  • TypeScript type definitions
Dependencies:
  • Minimal (only what's needed for core logic)
  • No UI framework dependencies
  • No platform-specific dependencies
Exports: 
export * from './domain';

export * from './services';


export * from './repositories';


export * from './utils';


export * from './types';

packages/web

Purpose: Web application (React) Contains:
  • React components
  • Feature modules
  • Pages/routes
  • React hooks
  • Context providers
  • Zustand stores
  • Web-specific utilities
  • Global styles
Dependencies:
  • React 18+
  • TypeScript
  • Tailwind CSS
  • Zustand
  • React Query
  • Three.js + React Three Fiber
  • packages/core (workspace dependency)
  • packages/components (workspace dependency)
Build Tool: Vite

packages/mobile (Future)

Purpose: Mobile application (React Native) Contains:
  • React Native components
  • Screens
  • Navigation
  • Mobile-specific utilities
Dependencies:
  • React Native
  • packages/core (workspace dependency)
  • packages/components (workspace dependency, may need RN-specific implementations)
Build Tool: Metro bundler

packages/desktop (Future)

Purpose: Desktop application (Electron/Tauri) Contains:
  • Main process (Electron/Tauri)
  • Renderer process (shares web UI)
  • Desktop-specific features
Dependencies:
  • Electron or Tauri
  • packages/web (workspace dependency - reuse web UI)
  • packages/core (workspace dependency)

packages/components

Purpose: Shared component library Contains:
  • Base components (Button, Input, Card, Modal, Typography)
  • Feature-specific components (Screening, Intervention, Visualization)
  • Theme system (default, dyslexia, high-contrast)
  • Component documentation
Dependencies:
  • React (for React implementation)
  • TypeScript
  • Tailwind CSS
  • packages/core (workspace dependency - for types)
Note: Could have multiple implementations (React, React Native) in future

Dependency Management Strategy

Workspace Dependencies

Install all workspace dependencies: 
npm install
Add dependency to specific package: 
npm install  --workspace=packages/web
Add dev dependency to specific package: 
npm install  -D --workspace=packages/core
Add workspace dependency: 
npm install @dyslexia-hub/core --workspace=packages/web

Version Management

Strategy: Semantic versioning (semver)
  • Major: Breaking changes
  • Minor: New features, backward compatible
  • Patch: Bug fixes, backward compatible
Workflow:
  • Use npm version to bump versions
  • Use conventional commits for changelog
  • Use semantic-release for automated releases (future)

Dependency Updates

Schedule: Monthly security updates, quarterly feature updates Tool: npm audit + Dependabot (GitHub) Process:
  1. Run npm audit to check for vulnerabilities
  2. Review Dependabot PRs
  3. Test updates in staging
  4. Deploy to production if tests pass

Efficient Build Strategy

Parallel Builds

Use npm workspaces for parallel builds: 
npm run build  # Builds all packages in parallel

Incremental Builds

Tool: Turbopack (future) or esbuild Strategy:
  • Only rebuild changed packages
  • Cache build artifacts
  • Watch mode for development

Build Order

Dependency Graph:
  1. core (no dependencies)
  2. components (depends on core)
  3. web (depends on core, components)
  4. mobile (depends on core, components) - future
  5. desktop (depends on web) - future
npm workspaces handles this automatically

Ease of Adding New Platforms

Adding a New Platform

Steps:
  1. Create new package: packages/new-platform/
  2. Add platform-specific dependencies
  3. Configure build tool for platform
  4. Import from @dyslexia-hub/core and @dyslexia-hub/components
  5. Implement platform-specific UI layer
  6. Add build script to root package.json
Example (Mobile): 
mkdir -p packages/mobile/src

cd packages/mobile


npm init -y


npm install react-native typescript


Add to root workspaces


npm install @dyslexia-hub/core @dyslexia-hub/components

Shared Code Reuse

Percentage of Shared Code:
  • Core business logic: 100% shared
  • Component library: 80% shared (20% platform-specific)
  • UI layer: 0% shared (platform-specific)
Overall: ~60-70% code reuse across platforms

Supports Parallel Development

Team Structure

Teams can work on different packages simultaneously:
  • Team A: Core business logic
  • Team B: Web application
  • Team C: Component library
  • Team D: Mobile (future)

Dependency Management

Independent Versioning:
  • Each package has its own version
  • Breaking changes require version bump
  • Semver for compatibility
Workspace Protocol:
  • Changes to core require testing in dependent packages
  • CI/CD runs tests for all affected packages
  • PRs should include test results

Summary

This monorepo structure provides:

  • Clear separation: Shared core vs. platform-specific code
  • Efficient builds: Parallel builds with npm workspaces
  • Easy platform addition: New platforms as new packages
  • Supports parallel development: Teams can work independently
  • Type safety: TypeScript across all packages
  • Consistent tooling: Shared linting, formatting, testing
  • Scalable: Can add more packages as needed
