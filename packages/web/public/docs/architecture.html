Dyslexia Grand Hub - Technical Architecture

Version: 1.0 Date: 2026-10-31 Author: Senior Tech Lead (Devin) Status: Architecture Phase - Complete

System Overview

The Dyslexia Grand Hub is a platform-agnostic, offline-first application designed to provide evidence-based dyslexia interventions, screening, and educational content. The architecture follows a layered approach with clear separation of concerns, enabling deployment across web, mobile, and desktop platforms while maintaining a shared core.

Core Business Logic Layer

Design Principles

1. Platform Agnosticism
  • Core business logic has no dependencies on UI frameworks
  • Pure TypeScript/JavaScript with standard interfaces
  • Testable without UI layer
  • Reusable across web, mobile, desktop
2. Framework Agnosticism
  • No framework-specific patterns in core
  • Dependency injection for all services
  • Plugin architecture for features
  • Standard JavaScript/TypeScript APIs only
3. Language Agnosticism
  • i18n support from day one
  • All user-facing strings externalized
  • ICU message format for complex translations
  • RTL support built-in
4. Offline-First
  • All core operations work offline
  • Local storage as primary, cloud as sync target
  • Background sync when online
  • Conflict resolution strategy

Separation of Concerns

UI Layer Responsibilities:
  • Render user interface
  • Handle user interactions

UI Layer Must NOT:

  • Implement domain rules
  • Handle data persistence

Data Layer Architecture

Repository Pattern

Agnostic Interface: 
interface Repository {

findById(id: string): Promise;


findAll(filters?: FilterOptions): Promise;


create(entity: T): Promise;


update(id: string, updates: Partial): Promise;


delete(id: string): Promise;


sync(): Promise;


}
Implementation Variants:
  • LocalRepository - SQLite/IndexedDB implementation
  • CloudRepository - PostgreSQL implementation (optional)
  • HybridRepository - Local with cloud sync

Local Storage Strategy

IndexedDB (Web):
  • User profiles and preferences
  • Screening results
  • Intervention progress
  • Offline cache of research claims
SQLite (Mobile/Desktop):
  • Same schema as IndexedDB
  • Cross-platform consistency
  • Migration strategy

Cloud Storage (Optional)

PostgreSQL Schema:
  • User accounts (for sync)
  • Research claims database (centralized)
  • Intervention metadata (updates)
  • Analytics (privacy-first)
Sync Strategy:
  • Local-first: primary storage is local
  • Cloud as backup and sync target
  • Background sync when online
  • Conflict resolution: last-write-wins with user prompt

Service Communication

Direct Service Calls:
  • Services call each other through interfaces
  • No circular dependencies
  • Event bus for async notifications

State Management Strategy

Local State (Component Level)

  • React state for UI state (loading, form inputs, modals)
  • Short-lived, component-scoped

Global State (Application Level)

  • Zustand or Redux Toolkit for cross-component state
  • User profile, screening results, active interventions
  • Persisted to local storage

Server State (Data Layer)

  • React Query or SWR for data fetching
  • Caching, invalidation, optimistic updates
  • Offline-first: cache first, network second

State Synchronization

  • Single source of truth: local storage
  • UI state derived from data state
  • Sync with cloud in background

Technology Stack Recommendations

Web Platform (MVP)

Frontend:
  • Framework: React 18+ with TypeScript
  • Justification: Large ecosystem, strong typing, excellent accessibility support, component reusability
Styling:
  • CSS Framework: Tailwind CSS
  • Justification: Utility-first, accessible by default, easy theming, excellent mobile support
State Management:
  • Library: Zustand
  • Justification: Simple API, TypeScript-first, no boilerplate, good performance
3D Visualization:
  • Library: Three.js + React Three Fiber
  • Justification: Industry standard, React integration, excellent performance, fallback to 2D
Build Tool:
  • Tool: Vite
  • Justification: Fast HMR, modern, simple config, excellent TypeScript support
Testing:
  • Unit: Jest + React Testing Library
  • E2E: Playwright
  • Accessibility: axe-core
  • Justification: Industry standards, excellent coverage, accessibility testing built-in

Mobile Platform (Post-MVP)

Option A: React Native
  • Pros: Shares React codebase, large ecosystem, TypeScript support
  • Cons: Native modules needed for some features
  • Recommendation: If web uses React
Option B: Flutter
  • Pros: Single codebase, excellent performance, Dart type safety
  • Cons: Different language (Dart), no code sharing with web
  • Recommendation: If cross-platform performance is critical

Desktop Platform (Future)

Option A: Electron
  • Pros: Web tech to desktop, large ecosystem, easy migration from web
  • Cons: Heavy resource usage
  • Recommendation: If resource usage is not critical
Option B: Tauri
  • Pros: Lightweight, Rust-based, secure
  • Cons: Smaller ecosystem, Rust learning curve
  • Recommendation: If performance and security are critical

Backend (Optional - Cloud Sync)

API:
  • Framework: Node.js + Express or Python + FastAPI
  • Justification: Express: familiar, FastAPI: type-safe, fast
Database:
  • Primary: PostgreSQL
  • Justification: ACID compliance, JSON support, excellent scalability
Authentication:
  • Service: Auth0 or Firebase Auth
  • Justification: OAuth 2.0, social login, secure
Hosting:
  • Frontend: Vercel or Netlify
  • Backend: Railway or Render
  • Justification: Easy deployment, automatic HTTPS, generous free tiers

Offline-First Architecture

Service Worker Strategy

Cache Strategy:
  • Static assets: Cache First (immediate load)
  • API calls: Network First (fetch fresh, fallback to cache)
  • Research claims: Cache First (update in background)
  • User data: Network First (sync when online)

Sync Strategy

Sync Flow:
  1. User comes online
  2. Check for local changes
  3. Push local changes to cloud
  4. Pull cloud changes to local
  5. Resolve conflicts (last-write-wins with user prompt)
  6. Update sync status
Conflict Resolution: 
interface SyncConflict {

entityType: string;


entityId: string;


localVersion: any;


cloudVersion: any;

}



interface Resolution {

result: any;


}

Security Considerations

Data Privacy

Local-First:
  • Primary storage is local
  • User data never leaves device without consent
  • Cloud sync is opt-in
Cloud Sync (if enabled):
  • End-to-end encryption for sensitive data
  • GDPR compliant
  • Minimal data collection

Authentication (if cloud sync)

OAuth 2.0:
  • Social login (Google, GitHub)
  • No password storage
  • Secure token handling

Content Security

XSS Prevention:
  • React auto-escapes by default
  • Content Security Policy headers
  • Sanitize user input
CSRF Prevention:
  • SameSite cookies
  • CSRF tokens for API calls

Performance Optimization

Code Splitting

Route-Based Splitting: 
const BrainShowcase = lazy(() => import('./modules/BrainShowcase'));

const DevelopmentalDisplay = lazy(() => import('./modules/DevelopmentalDisplay'));
Component-Based Splitting:
  • Load 3D components only when needed
  • Lazy load heavy visualizations

Asset Optimization

Images:
  • WebP format with fallbacks
  • Responsive images
  • Lazy loading
Fonts:
  • Subset fonts (only needed characters)
  • Preload critical fonts
  • Fallback fonts

Caching Strategy

HTTP Caching:
  • Static assets: Long cache (1 year)
  • API responses: Short cache (5 minutes)
  • Research claims: Medium cache (1 day)
Service Worker Caching:
  • Precache critical assets
  • Cache on-demand for others
  • Stale-while-revalidate for dynamic content

Scalability Considerations

Horizontal Scaling

Web:
  • CDN for static assets
  • Edge functions for API (if backend needed)
  • Stateless design for easy scaling
Database:
  • Read replicas for research claims
  • Connection pooling
  • Query optimization

Vertical Scaling

Performance Budgets:
  • Initial load: <3s
  • Time to interactive: <5s
  • First contentful paint: <1.5s
  • Largest contentful paint: <2.5s
Bundle Size:
  • Core bundle: <200KB gzipped
  • Route bundles: <100KB gzipped each
  • Total: <500KB gzipped

Conclusion

This architecture provides:

  • Platform Agnosticism: Shared core across web, mobile, desktop
  • Framework Agnosticism: No lock-in, plugin architecture
  • Language Agnosticism: i18n support from day one
  • Offline-First: Works without internet, syncs when online
  • Modularity: Clear module boundaries, plugin system
  • Scalability: Performance budgets, caching strategy
  • Accessibility: Built-in from day one
  • Privacy: Local-first, opt-in cloud sync
