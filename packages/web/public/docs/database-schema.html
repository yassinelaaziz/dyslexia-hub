Table Definitions

Local Storage Schema (IndexedDB/Web)

Users

interface UserRecord {

id: string; // UUID


age: number;


language: string; // ISO 639-1 code (e.g., 'en', 'es')


createdAt: Date;


updatedAt: Date;


preferences: UserPreferences;


}



interface UserPreferences {


theme: 'default' | 'dyslexia' | 'high-contrast';


fontSize: 'small' | 'medium' | 'large' | 'extra-large';


fontFamily: 'default' | 'opendyslexic';


lineSpacing: number; // 1.0 - 2.0


letterSpacing: number; // 0 - 5px


enableSoundEffects: boolean;


enableAnimations: boolean;


enableOfflineMode: boolean;


enableCloudSync: boolean;


}
Indexes:
  • Primary: id
  • Index: language
  • Index: createdAt

ScreeningResults

interface ScreeningResultRecord {

id: string; // UUID


userId: string; // FK to Users


date: Date;


age: number;


version: string; // Screening version


scores: ScreeningScores;


severity: SeverityLevel;


recommendations: string[]; // Intervention IDs


}



interface ScreeningScores {


phonological: number; // 0-100


rapidNaming: number; // 0-100


visual: number; // 0-100


workingMemory: number; // 0-100


overall: number; // 0-100


}



type SeverityLevel = 'none' | 'mild' | 'moderate' | 'severe';
Indexes:
  • Primary: id
  • Index: userId
  • Index: date
  • Index: severity
  • Compound: [userId, date]

InterventionProgress

interface InterventionProgressRecord {

id: string; // UUID


userId: string; // FK to Users


interventionId: string; // FK to Interventions


startDate: Date;


lastSessionDate: Date;


sessionsCompleted: number;


totalDuration: number; // minutes


progressScore: number; // 0-100


notes: ProgressNote[];


status: 'active' | 'paused' | 'completed' | 'abandoned';


}



interface ProgressNote {


date: Date;


content: string;


type: 'manual' | 'automatic';


}
Indexes:
  • Primary: id
  • Index: userId
  • Index: interventionId
  • Index: status
  • Compound: [userId, interventionId]

name: string;

ageRange: [number, number]; // [min, max]

evidenceCount: number; // Number of supporting claims

}



type InterventionCategory =


| 'phonological'


| 'RAN'


| 'neurofeedback'


| 'BCI'


| 'multisensory'


| 'environmental'


| 'technological';



interface InterventionGuide {


steps: GuideStep[];


duration: number; // minutes per session


frequency: string; // e.g., '3x per week'


materials: string[];

}



interface GuideStep {

description: string;


duration: number; // minutes

Indexes:

  • Index: efficacyRating

Cloud Storage Schema (PostgreSQL - Optional)

Users (Cloud)

CREATE TABLE users (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),


email VARCHAR(255) UNIQUE NOT NULL,


password_hash VARCHAR(255) NOT NULL,


age INTEGER,


language VARCHAR(10) NOT NULL DEFAULT 'en',


created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),


updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),


preferences JSONB NOT NULL DEFAULT '{}',


cloud_sync_enabled BOOLEAN DEFAULT FALSE,


last_synced_at TIMESTAMP WITH TIME ZONE


);



CREATE INDEX idx_users_email ON users(email);


CREATE INDEX idx_users_language ON users(language);


CREATE INDEX idx_users_last_synced ON users(last_synced_at);

CREATE TABLE screening_results (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),


user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,


date TIMESTAMP WITH TIME ZONE NOT NULL,


age INTEGER NOT NULL,


version VARCHAR(50) NOT NULL,


scores JSONB NOT NULL,


severity VARCHAR(20) NOT NULL,


recommendations TEXT[] NOT NULL,


created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()


);



CREATE INDEX idx_screening_user_id ON screening_results(user_id);


CREATE INDEX idx_screening_date ON screening_results(date);


CREATE INDEX idx_screening_severity ON screening_results(severity);


CREATE INDEX idx_screening_user_date ON screening_results(user_id, date);

CREATE TABLE interventions (

target_deficit TEXT[] NOT NULL,

age_max INTEGER NOT NULL,

evidence_count INTEGER NOT NULL DEFAULT 0,


description TEXT NOT NULL,


guide JSONB NOT NULL,


created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),


updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()


);



CREATE INDEX idx_interventions_category ON interventions(category);


CREATE INDEX idx_interventions_efficacy ON interventions(efficacy_rating);


CREATE INDEX idx_interventions_age_range ON interventions(age_min, age_max);


CREATE INDEX idx_interventions_updated ON interventions(updated_at);

CREATE TABLE claims (

CREATE INDEX idx_claims_source_id ON claims(source_id);


CREATE INDEX idx_claims_phase ON claims(phase);

Indexes for Performance

Local Storage (IndexedDB)

Performance Considerations:
  • IndexedDB automatically indexes primary keys
  • Create additional indexes for frequently queried fields
  • Use compound indexes for multi-field queries
Critical Indexes:
  • ScreeningResult[userId, date] - For user's screening history
  • InterventionProgress[userId, interventionId] - For user's progress on specific intervention
  • Claim[phase] - For filtering by research phase
  • Claim[topics] - For topic-based searches

Cloud Storage (PostgreSQL)

Performance Considerations:
  • B-tree indexes for equality and range queries
  • GIN indexes for JSONB fields
  • Partial indexes for filtered queries
  • Covering indexes for frequently accessed columns
Critical Indexes:
  • B-tree on foreign keys (automatic)
  • B-tree on frequently filtered columns (category, severity, phase)
  • GIN on JSONB fields (scores, preferences, guide)
  • Compound indexes for common query patterns
  • Partial indexes for active records only

Relationships

One-to-Many

User → ScreeningResults
  • One user can have many screening results
  • Cascade delete: If user deleted, delete all screening results
User → InterventionProgress
  • One user can track progress on many interventions
  • Cascade delete: If user deleted, delete all progress
Intervention → InterventionProgress
  • One intervention can have many progress records (different users)
  • No cascade: Intervention is read-only reference data
Source → Claims
  • One source can have many claims
  • No cascade: Source is read-only reference data

Many-to-Many

Claim ↔ Topics
  • One claim can have many topics
  • One topic can have many claims
  • Junction table: claim_topics

Data Migration Strategy

Automatic Migrations:
  • On app startup, check current schema version
  • Apply pending migrations in order
  • Create backup before migration
  • Rollback on failure
Backward Compatibility:
  • Maintain support for previous schema versions for grace period
  • Transform data during migration
  • Validate data integrity after migration

Data Integrity

Constraints

Local Storage (IndexedDB):
  • Primary key uniqueness (enforced by IndexedDB)
  • Foreign key relationships (application-level validation)
  • Required fields (application-level validation)
Cloud Storage (PostgreSQL):
  • Primary key uniqueness (enforced by database)
  • Foreign key constraints (enforced by database)
  • NOT NULL constraints (enforced by database)
  • CHECK constraints (enforced by database)
  • UNIQUE constraints (enforced by database)

Data Privacy

Sensitive Data

Types of Sensitive Data:
  • Screening results (potentially stigmatizing)
  • Intervention progress (learning disability indicators)
  • User preferences (personalization data)
Protection Strategies:
  • Local-first: Primary storage is local
  • Encryption at rest (for cloud sync)
  • No PII in reference data (interventions, claims, sources)
  • Anonymized analytics (if enabled)

Cloud Sync Privacy

Opt-In Only:
  • User must explicitly enable cloud sync
  • Clear explanation of what data is synced
  • Ability to delete cloud data
Encryption:
  • End-to-end encryption for sensitive fields
  • Encryption keys stored locally
  • Server cannot decrypt user data

Data Synchronization

Sync Flow

Local to Cloud:
  1. User completes screening (offline)
  2. Data saved to IndexedDB
  3. User comes online
  4. Background sync triggers
  5. Push screening result to cloud
  6. Cloud validates and stores
  7. Sync metadata updated
Cloud to Local:
  1. Research repository updated (new claims added)
  2. Cloud data updated
  3. User comes online
  4. Background sync triggers
  5. Pull updated claims from cloud
  6. Update local IndexedDB
  7. Sync metadata updated

Conflict Resolution

Strategies:
  1. Last-Write-Wins: Most recent change wins (default)
  2. Manual Resolution: User prompted to choose
  3. Merge: Automatic merge if possible (e.g., additive arrays)
Conflict Types:
  • Same record modified locally and cloud
  • Record deleted locally but exists in cloud
  • Record added locally and cloud with same ID
Resolution Logic: 
function resolveConflict(conflict: SyncConflict): Resolution {

const localTimestamp = new Date(conflict.localVersion.updatedAt);


const cloudTimestamp = new Date(conflict.cloudVersion.updatedAt);



if (localTimestamp > cloudTimestamp) {


return { strategy: 'local', result: conflict.localVersion };


} else if (cloudTimestamp > localTimestamp) {


return { strategy: 'cloud', result: conflict.cloudVersion };


} else {


// Same timestamp - merge if possible


return mergeRecords(conflict.localVersion, conflict.cloudVersion);


}


}

Backup and Recovery

Local Backup

Strategy:
  • Periodic export of IndexedDB to JSON
  • User can manually trigger backup
  • Backup includes all user data (not reference data)
Backup Format: 
{

"version": "1.0.0",


"exportDate": "2026-10-31T00:00:00Z",


"users": [...],


"screeningResults": [...],


"interventionProgress": [...]


}

Cloud Backup

Strategy:
  • Automatic daily backups (PostgreSQL)
  • Point-in-time recovery (PITR)
  • Geographic redundancy (multi-region)
Retention:
  • Daily backups: 30 days
  • Weekly backups: 12 weeks
  • Monthly backups: 12 months

Performance Optimization

Query Optimization

IndexedDB:
  • Use indexes for filtered queries
  • Limit result sets with pagination
  • Use cursor-based iteration for large datasets
PostgreSQL:
  • Use EXPLAIN ANALYZE for query planning
  • Add covering indexes for frequent queries
  • Use materialized views for complex aggregations
  • Partition large tables by date (if needed)

Caching Strategy

Application-Level:
  • Cache frequently accessed data in memory
  • Cache invalidation on data changes
  • TTL-based cache expiration
Reference Data:
  • Interventions, claims, sources cached locally
  • Update in background when online
  • Stale-while-revalidate strategy

Summary

This database schema provides:

  • Normalized Design: 3NF compliance, clear relationships
  • Clear Relationships: One-to-many, many-to-many defined
  • Performance Considerations: Strategic indexes, caching
  • Offline-Capable: IndexedDB/SQLite for local storage
  • Sync Strategy: Local-first with optional cloud sync
  • Data Integrity: Constraints and validation
  • Privacy Protection: Local-first, opt-in cloud sync, encryption
  • Migration Strategy: Versioned schema, automatic migrations
  • Backup/Recovery: Local export, cloud backups
